# فاز دو: احراز هویت

این فاز API ثبت‌نام، ورود، خروج و یک مسیر محافظت‌شده را اضافه می‌کند. فرایند تأیید 2FA در فاز سه اضافه شده و در [راهنمای دومرحله‌ای](two-factor.fa.md) توضیح داده شده است. رابط کاربری فرم‌ها هنوز پیاده‌سازی نشده است.

## مسیرها

همه مسیرها با `/api/auth` شروع می‌شوند و پاسخ‌های حساس `Cache-Control: no-store` دارند.

| متد و مسیر     | ورودی                           | نتیجه موفق                           |
| -------------- | ------------------------------- | ------------------------------------ |
| `POST /signup` | JSON شامل `email` و `password`  | ۲۰۱، اطلاعات عمومی کاربر و کوکی ورود |
| `POST /login`  | JSON شامل `email` و `password`  | ۲۰۰، اطلاعات عمومی کاربر و کوکی ورود |
| `GET /me`      | کوکی معتبر                      | ۲۰۰، شناسه و ایمیل کاربر             |
| `POST /logout` | کوکی معتبر و بدنه JSON مثل `{}` | ۲۰۴، ابطال نشست فعلی و پاک‌شدن کوکی  |

ثبت‌نام کاربر را وارد هم می‌کند. ایمیل قبل از ذخیره و جست‌وجو trim و lowercase می‌شود؛ پسورد trim نمی‌شود. پسورد ثبت‌نام باید ۸ تا ۱۲۸ کاراکتر باشد. ایمیل باید معتبر و حداکثر ۲۵۴ کاراکتر باشد. فیلدهای اضافی مثل `role` یا `passwordHash` پذیرفته نمی‌شوند. بدنه درخواست حداکثر ۸ کیلوبایت است.

پاسخ کاربر فقط شامل `id` و `email` است. هش پسورد، راز 2FA، کدهای بازیابی و JWT در JSON پاسخ قرار نمی‌گیرند.

| وضعیت     | معنا                                            |
| --------- | ----------------------------------------------- |
| ۴۰۰       | ورودی یا JSON نامعتبر                           |
| ۴۰۱       | ایمیل/پسورد نادرست یا نشست نامعتبر/منقضی/لغوشده |
| ۴۰۳       | Origin مجاز نیست                                |
| ۴۰۹       | ایمیل قبلاً ثبت شده است                         |
| ۴۱۳ / ۴۱۵ | بدنه بیش از حد مجاز / Content-Type غیر JSON     |
| ۴۲۹       | محدودیت تعداد درخواست؛ همراه `Retry-After`      |
| ۵۰۳       | تنظیمات احراز هویت یا سرویس دیتابیس آماده نیست  |

## پسورد و JWT

پسورد حساب‌های جدید با Argon2id، salt تصادفی، حافظه ۶۴ مگابایت، سه تکرار و parallelism یک هش می‌شود. ورود برای ایمیل ناشناخته و پسورد اشتباه پاسخ یکسان دارد؛ برای حساب ناشناخته نیز بررسی هش انجام می‌شود.

JWT با HS256 امضا می‌شود و شامل شناسه کاربر، شناسه نشست، زمان صدور/انقضا، issuer و audience است. عمر نشست یک ساعت است؛ refresh token و تمدید خودکار در این فاز نداریم.

کوکی `contacts_session` دارای `HttpOnly`، `SameSite=Lax` و `Path=/api` است. در محیط HTTPS باید `Secure` فعال باشد. توکن در localStorage ذخیره نمی‌شود.

## خروج و محافظت مسیرها

جدول `AuthSession` شناسه نشست، مالک، زمان ساخت و انقضا را نگه می‌دارد؛ خود JWT در دیتابیس ذخیره نمی‌شود. Middleware `requireAuth` امضا و claims را بررسی می‌کند و وجود نشست معتبر و صاحب آن را از دیتابیس تأیید می‌کند. نشست حذف‌شده، منقضی یا متعلق به کاربر دیگر پاسخ ۴۰۱ می‌گیرد.

خروج، نشست فعلی را حذف می‌کند؛ بنابراین حتی نسخه کپی‌شده همان کوکی بعد از خروج معتبر نیست. نشست‌های دیگر کاربر دست‌نخورده می‌مانند. حذف کاربر نشست‌هایش را با cascade پاک می‌کند. رکوردهای منقضی دسترسی ایجاد نمی‌کنند؛ پاک‌سازی دوره‌ای آن‌ها هنوز زمان‌بندی نشده و می‌تواند در فاز عملیات اضافه شود.

برای مسیرهای آینده، `requireAuth()` را قبل از handler قرار دهید. شناسه کاربر احرازشده از `response.locals.auth.user.id` خوانده می‌شود؛ آن را از بدنه درخواست کاربر نگیرید. صرف احراز هویت جای کنترل مالکیت مخاطب را نمی‌گیرد.

اگر `twoFactorEnabled=true` باشد، ورود با پسورد پاسخ ۲۰۲ با `twoFactorRequired: true` می‌دهد و فقط کوکی چالش موقت صادر می‌کند. نشست کامل بعد از تأیید TOTP یا کد بازیابی در `/2fa/verify` صادر می‌شود. نشست‌های بدون تأیید دومرحله‌ای به مسیر محافظت‌شده دسترسی ندارند.

## Origin، CORS و محدودیت درخواست

درخواست دارای Origin فقط از `APP_ORIGIN` پذیرفته می‌شود. CORS برای همان origin و با credentials فعال است. درخواست‌های POST فقط `application/json` می‌پذیرند؛ این محدودیت همراه بررسی Origin و SameSite از ارسال فرم‌های بین‌سایتی برای تغییر نشست جلوگیری می‌کند. کلاینت‌های غیرمرورگری بدون Origin می‌توانند JSON ارسال کنند.

ورود حداکثر ۱۰ درخواست در ۱۵ دقیقه و ثبت‌نام حداکثر ۵ درخواست در ساعت برای هر IP دارد؛ درخواست‌های موفق هم شمرده می‌شوند. شمارنده فعلی در حافظه هر پردازش است و با restart پاک می‌شود. قبل از اجرای چند نمونه بک‌اند، یک store مشترک مثل Redis لازم است. `trust proxy` عمداً به‌صورت عمومی فعال نشده؛ در استقرار پشت reverse proxy باید تعداد/آدرس proxyهای واقعی مشخص شود تا IP درست باشد و جعل `X-Forwarded-For` محدودیت را دور نزند.

## تنظیمات محلی و Docker

در `.env` ریشه:

```dotenv
JWT_SECRET=<random-secret-at-least-32-characters>
APP_ORIGIN=http://localhost:3000
AUTH_COOKIE_SECURE=false
```

برای ساخت یک secret تصادفی مستقل، خروجی دستور زیر را فقط در `.env` ذخیره کنید:

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

بدون secret معتبر، ثبت‌نام و ورود خطای ۵۰۳ می‌دهند؛ هیچ کلید پیش‌فرضی وجود ندارد. تغییر secret، توکن‌های صادرشده با کلید قبلی را نامعتبر می‌کند. حالت `AUTH_COOKIE_SECURE=false` فقط برای HTTP محلی است؛ برای دامنه نهایی HTTPS مقدار را `true` و `APP_ORIGIN` را آدرس واقعی فرانت قرار دهید. اگر این متغیر حذف شود، محیط production به‌صورت پیش‌فرض Secure است.

```bash
npm run db:migrate
docker compose up --build --wait
```

مایگریشن `20260928100000_auth_sessions` فقط جدول نشست‌ها و رابطه/ایندکس‌های آن را اضافه می‌کند. برای اجرای مایگریشن از Docker، فرمان فاز یک همچنان معتبر است.

در فرانت برای تمام درخواست‌های احراز هویت از `credentials: 'include'` استفاده کنید:

```javascript
const response = await fetch('http://localhost:4000/api/auth/me', {
  credentials: 'include',
});
```

## بررسی

```bash
npm run check
npm run test:auth
```

برای دستور دوم باید `DATABASE_TEST_URL` به دیتابیس توسعه/تست مایگریت‌شده اشاره کند. تست احراز هویت از HTTP واقعی و PostgreSQL استفاده می‌کند؛ یک کاربر با ایمیل تصادفی `auth-test-…@contacts.example` می‌سازد و در پایان فقط همان کاربر و نشست‌هایش را حذف می‌کند. در صورت قطع اجباری فرایند ممکن است آن حساب آزمایشی باقی بماند.

این تست ثبت‌نام، ورود، خروج، عدم امکان استفاده مجدد از توکن خروج‌شده، کوکی، محدودیت درخواست، اعتبارسنجی، ایمیل تکراری، Origin، انقضای توکن/نشست و عدم دورزدن 2FA را بررسی می‌کند.

حساب seed فاز یک رمز تصادفی دورریخته‌شده دارد و برای ورود استفاده نمی‌شود؛ برای آزمون دستی یک حساب جدید ثبت کنید.
