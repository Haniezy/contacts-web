# فاز ۶: لندینگ و احراز هویت فرانت

## مسیرها

- `/`: لندینگ بدون هدر، با دکمه‌های ورود و ساخت حساب. مطابق ویدئوی طرح، سه گوشی پس از ورود از پایین ظاهر می‌شوند و هر ۳٫۷ ثانیه یکی به‌ترتیب ورود، فهرست مخاطبین و جزئیات مخاطب جلو می‌آید؛ بقیه کم‌رنگ و محو می‌شوند و توضیح همان گوشی در کپسول پایین صفحه نمایش داده می‌شود. نگه‌داشتن نشانگر روی یک گوشی آن را جلو می‌آورد. انتخاب نقطه‌های کپسول چرخش خودکار را متوقف می‌کند. با تنظیم کاهش حرکت دستگاه، چرخش و انیمیشن‌ها اجرا نمی‌شوند.
- کاربری که وارد حسابش است (به درخواست صاحب پروژه، ۱۳ مهر ۱۴۰۵) در لندینگ به‌جای «ساخت حساب» و «ورود» فقط دکمه «ورود به دفترچه» به `/contacts` را می‌بیند؛ بقیه صفحه یکسان است. اگر بررسی نشست ممکن نباشد، نسخه بدون ورود نمایش داده می‌شود. خروج همچنان به `/login` می‌رود.
- زیر بخش بالایی لندینگ، به درخواست صاحب پروژه (۱۳ مهر ۱۴۰۵) این بخش‌ها اضافه شدند: «ویژگی‌ها» (شش کارت)، «امنیت و حریم خصوصی» (چهار کارت)، «سوالات متداول» (هر بار فقط یک جواب باز است و با انیمیشن نرم ۳۰۰ میلی‌ثانیه‌ای باز و بسته می‌شود، مثل کارت‌های تنظیمات؛ در کاهش حرکت بدون انیمیشن)، «درباره دفترچه» با ایمیل تماس، و فوتر با نام برنامه، نسخه از `package.json` و همان سوییچ‌های زبان و تم تنظیمات (ایمیل تماس به درخواست صاحب پروژه فقط در «درباره دفترچه» است). متن‌ها فقط قابلیت‌های واقعی برنامه را می‌گویند؛ نظر کاربر، آمار، قیمت و سوال «رایگان است؟» به تصمیم صاحب پروژه حذف شده‌اند. برای این بخش‌ها طرح جداگانه‌ای نیست؛ از کارت‌های صفحه تنظیمات و توکن‌های موجود ساخته شده‌اند. بخش بالایی پس‌زمینه گرادیان خودش را گرفت تا با بلندتر شدن صفحه تغییر نکند، در موبایل تیتر ۲۴ پیکسل است تا در یک خط جا شود (در انگلیسی دو خط متوازن) و دکمه‌ها ۱۵۰×۴۶ هستند؛ متن دکمه‌ها ۱۹ پیکسل ضخیم می‌ماند چون با اندازه کوچک‌تر، رنگ دکمه ورود کنتراست کافی ندارد. در دسکتاپ گوشی‌ها ۴۰ پیکسل پایین‌تر از طرح (از ۳۷۶ پیکسل) شروع می‌شوند تا گوشی جلوآمده به دکمه‌ها نچسبد، و در تبلت ۷۶۸ تا ۱۰۲۳ ارتفاعش زیر گوشی‌ها تمام می‌شود تا نوار خالی بالای بخش‌ها نماند. متن کوچک و لینک‌ها روی رنگ انتهای صفحه با `--landing-text` و `--landing-link` کنتراست AA دارند. ایمیل تماس در `src/components/auth/landing-sections.tsx` است.
- `/signup`: نام، نام خانوادگی، ایمیل، رمز عبور و تکرار آن؛ پس از ثبت‌نام، ستاپ QR باز می‌شود.
- `/login`: ورود با ایمیل و رمز؛ حساب دارای 2FA به `/2fa` و حساب بدون آن به `/contacts` می‌رود.
- `/2fa/setup`: نمایش QR واقعی API، کلید دستی و کپی؛ ادامه به ورود کد شش‌رقمی و فعال‌سازی. پس از فعال‌سازی، ده کد بازیابی یک‌بارمصرف با امکان کپی و دانلود نمایش داده می‌شود. کاربر پس از ذخیره کدها وارد مخاطبین می‌شود.
- `/2fa`: کد برنامه احراز هویت یا کد بازیابی؛ ارقام فارسی و عربی نیز پذیرفته و برای API به انگلیسی تبدیل می‌شوند.
- `/contacts`: مقصد محافظت‌شده؛ از فاز ۷ صفحه کامل مخاطبین است ([راهنمای فاز ۷](contacts-frontend.fa.md)).

فعال‌سازی 2FA مطابق گزینه «فعلاً رد کن» در طرح اختیاری است. پس از فعال شدن، ورود بدون کد معتبر امکان‌پذیر نیست. گزینه فراموشی رمز عبور به تصمیم صاحب پروژه حذف شده است؛ لینک «رمز عبورم رو فراموش کردم» در طرح پیاده‌سازی نمی‌شود و هیچ API برای آن وجود ندارد.

## قرارداد فرم و داده

به تصمیم صاحب پروژه، رمز عبور ثبت‌نام در فرانت و API باید ۶ تا ۱۶ کاراکتر باشد. ورود هر رمز ذخیره‌شده تا ۱۲۸ کاراکتر را می‌پذیرد تا حساب‌های قدیمی قفل نشوند. نام و نام خانوادگی در مایگریشن `20260929150000_user_names` به مدل User اضافه شدند. نام‌ها در UI اجباری و در API برای سازگاری با کلاینت‌های قبلی اختیاری‌اند؛ نام ارسال‌شده باید ۲ تا ۱۶ و نام خانوادگی ۲ تا ۲۸ کاراکتر باشد. همین قانون‌ها در پروفایل هم برقرارند.

اگر دامنه ایمیل غلط تایپی یک سرویس معروف باشد (مثل `gmial.com` یا `gmail.co` به‌جای `gmail.com`)، ورود و ثبت‌نام آن را رد می‌کنند و «منظورت sara@gmail.com بود؟» را نشان می‌دهند؛ کلیک روی آدرس پیشنهادی آن را در فیلد می‌گذارد. API ثبت‌نام هم چنین ایمیلی را نمی‌پذیرد. فهرست سرویس‌ها در `frontend/src/lib/email.ts` و `backend/src/auth/email-typo.ts` است. دامنه‌های دیگر (ایمیل شرکتی، دانشگاهی یا نسخه‌های کشوری مثل `yahoo.fr`) مثل قبل پذیرفته می‌شوند. تکرار رمز فقط در فرانت اعتبارسنجی می‌شود و به API فرستاده نمی‌شود.

پیام‌های اعتبارسنجی، خطاهای سرور، اتمام نشست، کد اشتباه و محدودیت تعداد تلاش‌ها فارسی/انگلیسی هستند. UI هنگام ارسال درخواست، ارسال تکراری را می‌بندد. رمز قابل نمایش/پنهان‌سازی است؛ برای رمز و ایمیل autocomplete مناسب تنظیم شده است.

QR و راز ستاپ فقط در حافظه همان فرایند UI نگه داشته می‌شوند. پس از رفرش در میانه ستاپ، کاربر رمز خود را دوباره تأیید می‌کند تا QR تازه بگیرد. راز، رمز عبور و کدهای بازیابی در localStorage یا sessionStorage ذخیره نمی‌شوند. کدهای بازیابی فقط همان بار نمایش داده می‌شوند و باید قبل از ترک صفحه ذخیره شوند.

## مطابقت با طرح

ابعاد از طرح‌های صاحب پروژه اندازه‌گیری شده‌اند: صفحه‌های احراز هویت در موبایل روی عرض ۳۹۰ و در دسکتاپ (از ۱۰۲۴ پیکسل) روی ۱۲۸۰×۷۶۰، و لندینگ روی ۱۴۴۰×۹۰۰. چیدمان دسکتاپ با عرض صفحه به‌صورت تناسبی بزرگ و کوچک می‌شود و در ۱۹۲۰ پیکسل به همان اندازه تصویر طرح می‌رسد؛ متن و کنترل‌ها زیر ۱۲۸۰ کوچک‌تر از اندازه طرح نمی‌شوند. رنگ‌ها از توکن‌های `globals.css` هستند و مقادیر دکوراسیون (دایره، بلاب نعنایی، کره‌ها و سایه‌ها) از تصویرهای روشن و تاریک نمونه‌برداری شده‌اند.

در موبایل و تبلت، سربرگ ثبت‌نام (لکه نعنایی، برند و کره‌ها) عیناً مثل ورود است و فرم هم از همان ارتفاع شروع می‌شود. در طرح، لکه ثبت‌نام کوتاه‌تر بود و شعار زیر «دفترچه» از آن بیرون می‌زد؛ به تصمیم صاحب پروژه یکسان شد. در دسکتاپ دکوراسیون دو صفحه از اول یکی بود.

صفحه‌های ورود و ثبت‌نام یک دکمه گرد آبی برای «بازگشت به صفحه اصلی» دارند که روی لکه نعنایی کنار برند است: در موبایل و تبلت کنار آیکون دفترچه، و در دسکتاپ بالای عنوان «دفترچه». فیلدها کمی فاصله داخلی دارند تا متن به دو سر خط نچسبد. فیلدهایی که مرورگر خودکار پر می‌کند هم همان رنگ بقیه را دارند و رنگ پس‌زمینه مرورگر روی آن‌ها نمی‌آید.

متن‌هایی که در طرح موبایل و دسکتاپ متفاوت‌اند (شعار برند و عنوان و توضیح ستاپ QR) هر دو ترجمه شده‌اند و با CSS فقط نسخه همان اندازه نمایش داده می‌شود. کلید ستاپ واقعی ۳۲ کاراکتر است؛ برخلاف نمونه کوتاه طرح، در چند خط داخل همان کپسول قرار می‌گیرد. فرم‌ها `method="post"` دارند تا اگر پیش از بارگذاری کامل جاوااسکریپت ارسال شوند، رمز یا کد در آدرس صفحه قرار نگیرد.

## اتصال و حفاظت

مرورگر فقط با `/api/...` روی دامنه خود سایت صحبت می‌کند. از نسخه یک‌پروژه‌ای، API در همان برنامه Next.js اجرا می‌شود (`src/app/api/[...path]/route.ts` و `src/server`) و سرویس یا آدرس جدایی ندارد. `APP_ORIGIN` باید برابر آدرس عمومی سایت باشد.

کوکی نشست و چالش 2FA همچنان HttpOnly و SameSite=Lax هستند و مسیرشان `/` است تا صفحات سروری نیز بتوانند نشست را بررسی کنند. اصل JWT و نشست دیتابیس در API اعتبارسنجی می‌شوند؛ وجود کوکی به‌تنهایی اجازه دسترسی نمی‌دهد.

در Next.js 16 فایل `src/proxy.ts` نقش middleware را دارد: نبود کوکی روی مسیر محافظت‌شده را سریع به ورود هدایت می‌کند. صفحه سروری نیز نشست را با `/auth/me` تأیید می‌کند و API مخاطبین مجدداً مالکیت/نشست را بررسی می‌کند. در اختلال API یا دیتابیس، داده محافظت‌شده نمایش داده نمی‌شود.

درخواست‌های تغییردهنده API فقط JSON تا ۸ کیلوبایت و Origin مورد اعتماد را می‌پذیرند؛ حجم واقعی بدنه حتی بدون Content-Length کنترل می‌شود. پاسخ احراز هویت کش نمی‌شود و خطاهای داخلی به مرورگر نشت نمی‌کنند. محدودیت تعداد درخواست فعال است؛ روی Vercel هر کاربر با نشانی‌ای که Vercel در `X-Real-IP` می‌گذارد جدا شمرده می‌شود ([راهنمای استقرار](deployment.fa.md)). جاهای دیگر (مثل Docker محلی) نشانی کاربر معلوم نیست و همه یک سهمیه دارند.

## اجرا و تست

```bash
npm run db:migrate
npm run build
npm run lint
npm run typecheck
docker compose up -d --build --wait
```

برای تست مرورگر، `DATABASE_TEST_URL` باید به دیتابیس توسعه/تستِ دارای مایگریشن‌ها اشاره کند. آن را در محیط فرایند تست تنظیم کنید؛ مقدار واقعی در گیت قرار نمی‌گیرد.

```bash
npm run build
npx playwright install chromium
npm run test:e2e
```

تست‌ها برنامه را با تنظیمات تست (دیتابیس تست، کلیدهای مخصوص تست و سقف‌های بزرگ‌تر تعداد درخواست) روی ۳۱۰۰ بالا می‌آورند. مسیر واقعی ثبت‌نام، QR، تأیید TOTP، کد بازیابی، خروج، جلوگیری از ورود با کد غلط، کوکی جعلی، Origin نامعتبر، ولیدیشن، تم/زبان و رفرش در موبایل و دسکتاپ بررسی می‌شود. حساب‌های موقت با UUID ساخته و همان حساب‌ها در پایان پاک می‌شوند. trace مرورگر خاموش است تا رمز و رازهای موقت تست در گزارش ضبط نشوند.
