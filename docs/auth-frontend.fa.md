# فاز ۶: لندینگ و احراز هویت فرانت

## مسیرها

- `/`: لندینگ بدون هدر، با لوگو، تیتر، یک خط توضیح و دکمه‌های ساخت حساب و ورود در وسط صفحه اول. به درخواست صاحب پروژه (۲۲ مهر ۱۴۰۵) سه گوشی و شکل‌های تزئینی طرح قبلی حذف شدند و کل لندینگ (همراه بخش‌ها و فوتر) روی همان عکس صفحه ورود است: نسخه‌ای کمی تار (WebP ۱۰۰۰ پیکسلی، ۱۱ کیلوبایت، `public/landing/backdrop.webp`؛ از قبل تار شده تا مرورگر خودش تار نکند)، ثابت پشت صفحه، با رنگ تم مثل صفحه ورود و یک پرده هم‌رنگ صفحه. در حالت تاریک پرده یکدست ۴۵٪ است (همان که صاحب پروژه انتخاب کرد)؛ در حالت روشن از ۴۵٪ بالا به ۸۰٪ پایین می‌رسد تا پای تیره عکس متن را ناخوانا نکند. متن‌هایی که مستقیم روی عکس‌اند (تیترها، توضیح‌ها و فوتر) رنگ کامل متن را دارند و در حالت روشن کمی تیره‌تر (`--on-photo`)؛ کنتراستشان روی تیره‌ترین نقطه پشتشان در هر سه تم و هر دو حالت اندازه‌گیری شده است (کمترین: ۴٫۲ برای لوگو، ۴٫۹ برای متن‌های کوچک).
- کاربری که وارد حسابش است (به درخواست صاحب پروژه، ۲۲ مهر ۱۴۰۵؛ قبلاً یک دکمه «ورود به دفترچه» می‌دید) با باز کردن لندینگ مستقیم روی سرور به `/contacts` فرستاده می‌شود، مثل صفحه‌های ورود و ثبت‌نام؛ لندینگ در تاریخچه مرورگر هم نمی‌ماند. لندینگ برای کسی است که حساب ندارد یا واردش نیست. اگر بررسی نشست ممکن نباشد، لندینگ نمایش داده می‌شود. خروج همچنان به `/login` می‌رود.
- زیر بخش بالایی لندینگ، به درخواست صاحب پروژه (۱۳ مهر ۱۴۰۵) این بخش‌ها اضافه شدند: «ویژگی‌ها» (شش کارت)، «امنیت و حریم خصوصی» (چهار کارت)، «سوالات متداول» (هر بار فقط یک جواب باز است و با انیمیشن نرم ۳۰۰ میلی‌ثانیه‌ای باز و بسته می‌شود، مثل کارت‌های تنظیمات؛ در کاهش حرکت بدون انیمیشن)، «درباره دفترچه» با ایمیل تماس، و فوتر با نام برنامه، نسخه از `package.json` و همان سوییچ‌های زبان و تم تنظیمات (ایمیل تماس به درخواست صاحب پروژه فقط در «درباره دفترچه» است). متن‌ها فقط قابلیت‌های واقعی برنامه را می‌گویند؛ نظر کاربر، آمار، قیمت و سوال «رایگان است؟» به تصمیم صاحب پروژه حذف شده‌اند. برای این بخش‌ها طرح جداگانه‌ای نیست؛ از کارت‌های صفحه تنظیمات و توکن‌های موجود ساخته شده‌اند. در موبایل تیتر ۲۴ پیکسل است تا در یک خط جا شود (در انگلیسی دو خط متوازن) و دکمه‌ها ۱۵۰×۴۶ هستند؛ متن دکمه‌ها ۱۹ پیکسل ضخیم می‌ماند چون با اندازه کوچک‌تر، رنگ دکمه ورود کنتراست کافی ندارد. ایمیل تماس در `src/components/auth/landing-sections.tsx` است.
- `/signup`: نام، نام خانوادگی، ایمیل، رمز عبور و تکرار آن؛ پس از ثبت‌نام، ستاپ QR باز می‌شود.
- `/login`: ورود با ایمیل و رمز؛ حساب دارای 2FA به `/2fa` و حساب بدون آن به `/contacts` می‌رود.
- `/2fa/setup`: نمایش QR واقعی API، کلید دستی و کپی؛ ادامه به ورود کد شش‌رقمی و فعال‌سازی. پس از فعال‌سازی، ده کد بازیابی یک‌بارمصرف با امکان کپی و دانلود نمایش داده می‌شود. کاربر پس از ذخیره کدها وارد مخاطبین می‌شود.
- **روشن‌تر کردن کلید دستی (به درخواست صاحب پروژه، ۱۴ مهر ۱۴۰۵):** کلید کنار QR برای وارد کردن در اپ احراز هویت است، نه ورود به سایت؛ متنش «اسکن نمی‌شه؟ این کلید رو توی اپ احراز هویت وارد کن» است با راهنمای کوتاه «Enter a setup key» و دکمه «کپی کلید» / «کلید کپی شد». مرحله کد می‌گوید «کد ۶ رقمی‌ای که الان توی اپ احراز هویت می‌بینی…». اگر کلید راه‌اندازی (حروف و رقم، ۱۶ کاراکتر یا بیشتر) در خانه‌های کد پیست شود، خانه‌ها پر نمی‌شوند و پیام «این کلید راه‌اندازیه، نه کد…» نمایش داده می‌شود (همین در صفحه `/2fa`). ده کد بازیابی مثل قبل پس از فعال شدن موفق نمایش داده می‌شوند. دکمه‌های کپی کلید و کپی کدها هر کدام وضعیت جدای خود را دارند («کلید کپی شد» / «کدها کپی شد») که پس از ۲٫۵ ثانیه به حالت عادی برمی‌گردد؛ پیش‌تر کپی کلید باعث می‌شد دکمه کدهای بازیابی از همان اول «کپی شد» بنویسد.
- `/2fa`: کد برنامه احراز هویت یا کد بازیابی؛ ارقام فارسی و عربی نیز پذیرفته و برای API به انگلیسی تبدیل می‌شوند.
- `/contacts`: مقصد محافظت‌شده؛ از فاز ۷ صفحه کامل مخاطبین است ([راهنمای فاز ۷](contacts-frontend.fa.md)).

فعال‌سازی 2FA مطابق گزینه «فعلاً رد کن» در طرح اختیاری است. پس از فعال شدن، ورود بدون کد معتبر امکان‌پذیر نیست. گزینه فراموشی رمز عبور به تصمیم صاحب پروژه حذف شده است؛ لینک «رمز عبورم رو فراموش کردم» در طرح پیاده‌سازی نمی‌شود و هیچ API برای آن وجود ندارد.

## قرارداد فرم و داده

به تصمیم صاحب پروژه، رمز عبور ثبت‌نام در فرانت و API باید ۶ تا ۱۶ کاراکتر باشد. ورود هر رمز ذخیره‌شده تا ۱۲۸ کاراکتر را می‌پذیرد تا حساب‌های قدیمی قفل نشوند. نام و نام خانوادگی در مایگریشن `20260929150000_user_names` به مدل User اضافه شدند. نام‌ها در UI اجباری و در API برای سازگاری با کلاینت‌های قبلی اختیاری‌اند؛ نام ارسال‌شده باید ۲ تا ۱۶ و نام خانوادگی ۲ تا ۲۸ کاراکتر باشد. همین قانون‌ها در پروفایل هم برقرارند.

اگر دامنه ایمیل غلط تایپی یک سرویس معروف باشد (مثل `gmial.com` یا `gmail.co` به‌جای `gmail.com`)، ورود و ثبت‌نام آن را رد می‌کنند و «منظورت sara@gmail.com بود؟» را نشان می‌دهند؛ کلیک روی آدرس پیشنهادی آن را در فیلد می‌گذارد. API ثبت‌نام هم چنین ایمیلی را نمی‌پذیرد. فهرست سرویس‌ها در `frontend/src/lib/email.ts` و `backend/src/auth/email-typo.ts` است. دامنه‌های دیگر (ایمیل شرکتی، دانشگاهی یا نسخه‌های کشوری مثل `yahoo.fr`) مثل قبل پذیرفته می‌شوند. تکرار رمز فقط در فرانت اعتبارسنجی می‌شود و به API فرستاده نمی‌شود.

پیام‌های اعتبارسنجی، خطاهای سرور، اتمام نشست، کد اشتباه و محدودیت تعداد تلاش‌ها فارسی/انگلیسی هستند. UI هنگام ارسال درخواست، ارسال تکراری را می‌بندد. رمز قابل نمایش/پنهان‌سازی است؛ برای رمز و ایمیل autocomplete مناسب تنظیم شده است.

QR و راز ستاپ فقط در حافظه همان فرایند UI نگه داشته می‌شوند. پس از رفرش در میانه ستاپ، کاربر رمز خود را دوباره تأیید می‌کند تا QR تازه بگیرد. راز، رمز عبور و کدهای بازیابی در localStorage یا sessionStorage ذخیره نمی‌شوند. کدهای بازیابی فقط همان بار نمایش داده می‌شوند و باید قبل از ترک صفحه ذخیره شوند.

## مطابقت با طرح

ابعاد از طرح‌های صاحب پروژه اندازه‌گیری شده‌اند: صفحه‌های احراز هویت در موبایل روی عرض ۳۹۰ و در دسکتاپ (از ۱۰۲۴ پیکسل) روی ۱۲۸۰×۷۶۰، و لندینگ روی ۱۴۴۰×۹۰۰. چیدمان دسکتاپ با عرض صفحه به‌صورت تناسبی بزرگ و کوچک می‌شود و در ۱۹۲۰ پیکسل به همان اندازه تصویر طرح می‌رسد؛ متن و کنترل‌ها زیر ۱۲۸۰ کوچک‌تر از اندازه طرح نمی‌شوند. رنگ‌ها از توکن‌های `globals.css` هستند.

**ورود و ثبت‌نام: یک کارت (به درخواست صاحب پروژه، ۲۲ مهر ۱۴۰۵؛ از کد و ویدیویی که فرستاد).** هر دو فرم در یک کارت‌اند (`src/components/auth/auth-card.tsx`). نیمه عکس دعوت به فرم دیگر است («سلام! … ساخت حساب» کنار ورود، «خوش برگشتی … ورود» کنار ثبت‌نام) و با زدن دکمه‌اش در ۰٫۶۵ ثانیه به طرف دیگر کارت می‌لغزد، در حالی که فرم‌ها جا عوض می‌کنند و محو و ظاهر می‌شوند (فقط `translate` و `opacity`). آدرس هم بین `/login` و `/signup` عوض می‌شود (`pushState`)، پس دکمه Back مرورگر همان حرکت را برعکس اجرا می‌کند و `next` ورود حفظ می‌شود. فرمی که کنار می‌رود فقط تا پایان حرکت در صفحه می‌ماند. در فارسی همه‌چیز آینه‌ای است (عکس اول در چپ). روی موبایل (زیر ۷۶۸ پیکسل) عکس نواری بالای کارت است و فرم‌ها در جای خود عوض می‌شوند. عکس، کوه‌های مه‌آلود از Adrien Tutin در Unsplash (لایسنس رایگان Unsplash، [لینک](https://unsplash.com/photos/9erjfn6UsZg))، به‌صورت WebP ۱۱۰۰×۱۴۰۰ و ۸۲ کیلوبایت (کیفیت ۵۵؛ رنگ و سایه تم جزئیات فشرده‌سازی را می‌پوشاند) در `public/auth/hero.webp` است، همراه صفحه پیش‌بارگذاری می‌شود و رنگ تم با `mix-blend-mode: color` و شفافیت ۴۵٪ رویش می‌نشیند (در تم سبز، سبز تم به‌جای تأکید برنزه‌اش)؛ یک سایه رو به پایین متن روشن را خوانا نگه می‌دارد. رنگ دکمه‌ها و فیلدها از تم است. ورود با گوگل/فیسبوک/اپل، «مرا به خاطر بسپار» و «فراموشی رمز» که در طرح بودند ساخته نشدند، چون برنامه این امکان‌ها را ندارد. ثبت‌نام همان فیلدهای قبلی (نام، نام خانوادگی، ایمیل، رمز و تکرار آن) را دارد، پس کارت از طرح کمی پهن‌تر و بلندتر است (۷۶۰×۶۰۰). دکمه «بازگشت به صفحه اصلی» گوشه شروع صفحه است. صفحه‌های تأیید دو مرحله‌ای همان ظاهر قبلی (`AuthShell`) را دارند.

فیلدهایی که مرورگر خودکار پر می‌کند هم همان رنگ بقیه را دارند و رنگ پس‌زمینه مرورگر روی آن‌ها نمی‌آید.

## اتصال و حفاظت

مرورگر فقط با `/api/...` روی دامنه خود سایت صحبت می‌کند. از نسخه یک‌پروژه‌ای، API در همان برنامه Next.js اجرا می‌شود (`src/app/api/[...path]/route.ts` و `src/server`) و سرویس یا آدرس جدایی ندارد. `APP_ORIGIN` باید برابر آدرس عمومی سایت باشد.

کوکی نشست و چالش 2FA همچنان HttpOnly و SameSite=Lax هستند و مسیرشان `/` است تا صفحات سروری نیز بتوانند نشست را بررسی کنند. اصل JWT و نشست دیتابیس در API اعتبارسنجی می‌شوند؛ وجود کوکی به‌تنهایی اجازه دسترسی نمی‌دهد.

در Next.js 16 فایل `src/proxy.ts` نقش middleware را دارد: نبود کوکی روی مسیر محافظت‌شده را سریع به ورود هدایت می‌کند. صفحه سروری نیز نشست را با `/auth/me` تأیید می‌کند و API مخاطبین مجدداً مالکیت/نشست را بررسی می‌کند. در اختلال API یا دیتابیس، داده محافظت‌شده نمایش داده نمی‌شود.

درخواست‌های تغییردهنده API فقط JSON تا ۸ کیلوبایت و Origin مورد اعتماد را می‌پذیرند؛ حجم واقعی بدنه حتی بدون Content-Length کنترل می‌شود. پاسخ احراز هویت کش نمی‌شود و خطاهای داخلی به مرورگر نشت نمی‌کنند. محدودیت تعداد درخواست فعال است؛ روی Vercel هر کاربر با نشانی‌ای که Vercel در `X-Real-IP` می‌گذارد جدا شمرده می‌شود ([راهنمای استقرار](deployment.fa.md)). جاهای دیگر (مثل Docker محلی) نشانی کاربر معلوم نیست و همه یک سهمیه دارند.

## اجرا و تست

```bash
npm run db:migrate
npm run build
npm run lint
npm run typecheck
docker compose up -d --build --wait
```

برای تست مرورگر، `DATABASE_TEST_URL` باید به دیتابیس توسعه/تستِ دارای مایگریشن‌ها اشاره کند. آن را در محیط فرایند تست تنظیم کنید؛ مقدار واقعی در گیت قرار نمی‌گیرد.

```bash
npm run build
npx playwright install chromium
npm run test:e2e
```

تست‌ها برنامه را با تنظیمات تست (دیتابیس تست، کلیدهای مخصوص تست و سقف‌های بزرگ‌تر تعداد درخواست) روی ۳۱۰۰ بالا می‌آورند. مسیر واقعی ثبت‌نام، QR، تأیید TOTP، کد بازیابی، خروج، جلوگیری از ورود با کد غلط، کوکی جعلی، Origin نامعتبر، ولیدیشن، تم/زبان و رفرش در موبایل و دسکتاپ بررسی می‌شود. حساب‌های موقت با UUID ساخته و همان حساب‌ها در پایان پاک می‌شوند. trace مرورگر خاموش است تا رمز و رازهای موقت تست در گزارش ضبط نشوند.
