# فاز سه: احراز هویت دومرحله‌ای

این فاز TOTP شش‌رقمی، QR، فعال‌سازی پس از تأیید و ورود با TOTP یا کد بازیابی یک‌بارمصرف را اضافه می‌کند. همه مسیرها زیر `/api/auth` هستند. نمایش QR و فرم‌ها در فرانت هنوز پیاده‌سازی نشده؛ بک‌اند داده لازم را تحویل می‌دهد.

## راه‌اندازی

کاربر ابتدا وارد حساب می‌شود. سپس با کوکی ورود و پسورد فعلی درخواست زیر را می‌فرستد:

```text
POST /api/auth/2fa/setup
Content-Type: application/json
{ "password": "<current-password>" }
```

پاسخ شامل `secret` برای ورود دستی، `otpauthUri`، تصویر PNG در `qrCodeDataUrl` و `expiresAt` است. QR داخل بک‌اند ساخته می‌شود و راز به سرویس خارجی ارسال نمی‌شود. پاسخ `no-store` دارد؛ این داده‌ها را در لاگ یا analytics ثبت نکنید.

کاربر QR را در اپ سازگار با TOTP اسکن می‌کند و کد را به‌صورت **رشته شش‌رقمی** می‌فرستد؛ صفر ابتدای کد باید حفظ شود:

```text
POST /api/auth/2fa/confirm
{ "code": "<6-digits>" }
```

تا قبل از کد درست، `twoFactorEnabled` برابر false می‌ماند. راه‌اندازی ده دقیقه اعتبار دارد و به همان نشست درخواست‌کننده متصل است. پنج کد اشتباه آن را قفل می‌کند؛ برای شروع مجدد باید setup با پسورد انجام شود. حسابی که 2FA فعال دارد نمی‌تواند از setup برای جایگزینی راز فعلی استفاده کند.

در تأیید موفق، تمام نشست‌های قبلی لغو می‌شوند و یک نشست جدید با `twoFactorVerified=true` ایجاد می‌شود. پاسخ `{ enabled: true, recoveryCodes: [...] }` ده کد بازیابی را **فقط همان بار** نمایش می‌دهد. کاربر باید آن‌ها را امن نگه دارد؛ هیچ مسیر API برای خواندن دوباره متن آن‌ها وجود ندارد.

## ورود دومرحله‌ای

۱. درخواست `/login` با ایمیل و پسورد درست برای حساب دارای 2FA، پاسخ **۲۰۲** با `{ twoFactorRequired: true }` برمی‌گرداند. کوکی نشست مرورگر پاک و کوکی موقت `contacts_2fa_challenge` تنظیم می‌شود. این کوکی JWT ورود نیست و به `/me` یا مسیرهای محافظت‌شده دسترسی نمی‌دهد.

۲. مرورگر با `credentials: 'include'` مرحله دوم را انجام می‌دهد:

```text
POST /api/auth/2fa/verify
{ "code": "<6-digits>" }
```

یا در صورت نیاز به بازیابی:

```text
POST /api/auth/2fa/verify
{ "recoveryCode": "<one-unused-recovery-code>" }
```

فقط یکی از این دو فیلد پذیرفته می‌شود. کد بازیابی نیز به مرحله اولِ معتبر با پسورد نیاز دارد. استفاده از کد بازیابی، 2FA را غیرفعال نمی‌کند.

۳. پس از تأیید، کوکی موقت پاک و کوکی JWT معمولی صادر می‌شود؛ `/me` اکنون پاسخ ۲۰۰ می‌دهد. کد نادرست، منقضی یا قبلاً مصرف‌شده باعث صدور نشست نمی‌شود.

حساب‌هایی که هنوز 2FA را فعال نکرده‌اند، رفتار ورود فاز دو را دارند. نشست کاملی که قبلاً با هر دو عامل صادر شده تا خروج/انقضا معتبر می‌ماند؛ صرف شروع یک تلاش ورود جدید، سایر دستگاه‌های واردشده را خارج نمی‌کند.

## زمان و محدودیت تلاش

- TOTP با SHA1، شش رقم و دوره ۳۰ ثانیه ساخته می‌شود؛ اختلاف ساعت حداکثر یک دوره قبل/بعد پذیرفته می‌شود.
- بازه زمانی آخرین کد پذیرفته‌شده در دیتابیس ذخیره می‌شود. همان بازه دوباره پذیرفته نمی‌شود؛ کد تأیید فعال‌سازی هم مصرف‌شده محسوب می‌شود. برای ورود مجدد با TOTP باید کد بازه بعدی را استفاده کنید.
- چالش ورود پنج دقیقه اعتبار و حداکثر پنج تلاش ناموفق دارد. تلاش‌ها در دیتابیس هستند و restart بک‌اند شمارنده چالش را پاک نمی‌کند.
- پس از پنج خطا، حتی کد درست روی همان چالش پاسخ ۴۲۹ می‌گیرد؛ ورود از مرحله پسورد باید دوباره شروع شود.
- تمام مسیرهای `/2fa` یک محدودیت مشترک ۲۰ درخواست در ۱۵ دقیقه برای هر IP دارند؛ محدودیت مرحله پسورد هم برقرار است. محدودیت IP مانند فاز دو در حافظه است و برای چند replica به store مشترک نیاز دارد.

## ذخیره‌سازی و هم‌زمانی

راز TOTP با AES-256-GCM و nonce تصادفی رمزنگاری و با AAD به شناسه کاربر متصل می‌شود. دیتابیس متن راز را نگه نمی‌دارد. کلید رمزنگاری از JWT secret مستقل است.

چالش موقت یک توکن تصادفی ۲۵۶ بیتی است که فقط هش آن در جدول `LoginChallenge` ذخیره می‌شود. این توکن در کوکی HttpOnly با Path محدود به `/api/auth/2fa` قرار دارد.

هر کد بازیابی ۱۲۸ بیت تصادفی دارد و فقط هش SHA-256 وابسته به حساب آن ذخیره می‌شود. حروف بزرگ/کوچک و خط فاصله هنگام بررسی نرمال می‌شوند. آرایه هش‌ها بعد از مصرف کاهش می‌یابد.

عملیات حساس ابتدا ردیف User را با `FOR UPDATE` قفل می‌کنند. مصرف TOTP/کد بازیابی، حذف چالش و ایجاد نشست در یک تراکنش‌اند. بنابراین دو درخواست هم‌زمان نمی‌توانند همان کد بازیابی، همان TOTP یا همان چالش را دوبار مصرف کنند. فعال‌سازی هم با صدور نشست‌های مرحله پسورد هماهنگ شده است.

Middleware فقط نشست دارای تأیید دومرحله‌ای را برای کاربر دارای 2FA می‌پذیرد؛ نشست‌های قدیمی با پیش‌فرض `twoFactorVerified=false` قابل استفاده نیستند.

## تنظیمات

در `.env` محلی یک کلید ثابت و مستقل قرار می‌گیرد:

```dotenv
TWO_FACTOR_ENCRYPTION_KEY=<64-hex-characters>
```

تولید کلید برای محیط جدید:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

این کلید همراه سورس یا دیتابیس کامیت نمی‌شود و در Compose فقط به بک‌اند ارسال می‌شود. از آن نسخه پشتیبان امن نگه دارید؛ تعویض یا گم‌شدن آن باعث ناتوانی در خواندن رازهای قبلی می‌شود. چرخش کلید به مایگریشن رمزنگاری جداگانه نیاز دارد. بدون کلید معتبر setup/TOTP کار نمی‌کند؛ هیچ کلید جایگزین پیش‌فرضی وجود ندارد.

```bash
npm run db:migrate
docker compose up --build --wait
```

مایگریشن `20260928110000_two_factor` فیلدهای راه‌اندازی و جلوگیری از replay، پرچم تأیید نشست و جدول چالش را اضافه می‌کند.

## وضعیت و تست‌ها

`GET /api/auth/2fa/status` با نشست معتبر فقط `enabled` و `recoveryCodesRemaining` را برمی‌گرداند. خاموش کردن 2FA با `POST /api/auth/2fa/disable` و رمز عبور به‌همراه کد یا کد بازیابی انجام می‌شود ([فاز ۱۰](account.fa.md)).

```bash
npm run check
npm run test:auth
npm run test:2fa
```

تست‌های یکپارچه به `DATABASE_TEST_URL` برای یک دیتابیس توسعه/تست مایگریت‌شده نیاز دارند. تست 2FA با یک حساب تصادفی مستقل انجام می‌شود و در پایان همان حساب و نشست‌ها/چالش‌هایش حذف می‌شوند. زمان TOTP در تست تزریق می‌شود تا سناریوی بازه بعدی بدون انتظار واقعی آزمایش شود؛ مسیرهای عمومی هیچ پارامتری برای تغییر زمان ندارند.

غیرفعال‌سازی 2FA، صدور مجدد کدهای بازیابی و بازیابی حساب بدون داشتن هیچ‌کدام از عوامل در محدوده این فاز نیستند.
