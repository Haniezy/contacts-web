# فاز چهار: API مخاطبین

همه مسیرها زیر `/api/contacts` هستند و کوکی معتبر `contacts_session` می‌خواهند. اگر کاربر 2FA را فعال کرده باشد، نشست بدون تأیید مرحله دوم پذیرفته نمی‌شود. `userId` از نشست سرور گرفته می‌شود؛ فرانت اجازه ارسال یا تغییر آن را ندارد. شناسه مخاطب متعلق به کاربر دیگر، دقیقاً مانند شناسه ناموجود، پاسخ `404 CONTACT_NOT_FOUND` دارد.

## مسیرها

| متد    | مسیر                                  | کاربرد                     |
| ------ | ------------------------------------- | -------------------------- |
| GET    | `/api/contacts?q=&page=1&pageSize=20` | فهرست، جست‌وجو و صفحه‌بندی |
| POST   | `/api/contacts`                       | ساخت مخاطب                 |
| GET    | `/api/contacts/:id`                   | دریافت یک مخاطب            |
| PATCH  | `/api/contacts/:id`                   | تغییر فیلدهای ارسال‌شده    |
| DELETE | `/api/contacts/:id`                   | حذف مخاطب؛ پاسخ ۲۰۴        |
| POST   | `/api/contacts/:id/photo`             | آپلود یا جایگزینی عکس      |
| DELETE | `/api/contacts/:id/photo`             | حذف عکس مخاطب              |
| GET    | `/api/contacts/duplicates?by=phone`   | گروه‌های شماره تکراری      |
| GET    | `/api/contacts/duplicates?by=name`    | گروه‌های نام تکراری        |
| POST   | `/api/contacts/duplicates/ignore`     | نادیده گرفتن گروه شماره    |
| POST   | `/api/contacts/merge`                 | ادغام مخاطبین انتخاب‌شده   |

API ساخت/ویرایش و ادغام فقط JSON می‌پذیرد. پاسخ ساخت مخاطب ۲۰۱ است؛ خواندن، ویرایش، عکس و ادغام ۲۰۰ هستند. فیلدهای پاسخ مخاطب: `id`، `name`، `phone`، `photoUrl`، `birthday`، `reminder`، `createdAt` و `updatedAt`. شناسه داخلی فایل و شناسه مالک در پاسخ عمومی نمایش داده نمی‌شوند.

## ساخت و ویرایش

```json
{
  "name": "سارا احمدی",
  "phone": "+۹۸ (۹۱۲) ۳۴۵-۶۷۸۹",
  "birthday": "2000-02-29",
  "reminder": "همکار قدیمی"
}
```

نام و شماره برای ساخت اجباری‌اند؛ تاریخ تولد و یادداشت اختیاری هستند. نام پس از trim حداکثر ۲۰۰ کاراکتر و بدون نویسه کنترلی است. شماره ۳ تا ۱۵ رقم دارد تا شماره‌های کوتاه هم پشتیبانی شوند؛ `+` فقط در ابتدا مجاز است. ارقام فارسی/عربی به لاتین تبدیل و فاصله، پرانتز، نقطه و خط تیره حذف می‌شوند. مثال بالا به `+989123456789` تبدیل می‌شود. این اعتبارسنجی ساختاری است و فعال‌بودن شماره را تضمین نمی‌کند.

تاریخ تولد ورودی `YYYY-MM-DD` و تاریخ واقعی میلادی است؛ پاسخ تاریخ، ISO در نیمه‌شب UTC است و فرانت باید آن را به‌صورت تاریخ بدون تبدیل منطقه زمانی نمایش دهد. یادداشت حداکثر ۲۰۰۰ کاراکتر است. با `null` می‌توان تاریخ تولد یا یادداشت را پاک کرد. PATCH خالی، فیلد ناشناخته، `userId`، `id`، `photoUrl` و `photoKey` رد می‌شوند؛ عکس فقط از مسیر آپلود مدیریت می‌شود.

## جست‌وجو و صفحه‌بندی

```text
/api/contacts?q=علي&page=1&pageSize=20
/api/contacts?q=۹۱۲-۳۴۵&page=1&pageSize=10
```

جست‌وجوی نام شامل بخشی از نام، بدون حساسیت به بزرگی حروف لاتین و با یکسان‌سازی `ي/ی` و `ك/ک` است. جست‌وجوی شماره ارقام فارسی/عربی و جداکننده‌ها را یکسان می‌کند. `%` و `_` نویسه عادی‌اند، نه wildcard؛ کوئری‌ها پارامتری هستند. جست‌وجو هیچ‌گاه مخاطبین دیگر کاربران را برنمی‌گرداند.

مرتب‌سازی الفبایی با collation مبتنی بر ICU در PostgreSQL انجام می‌شود و حروف فارسی مانند «ب، پ، ت، چ» درست مرتب می‌شوند. برای نام‌های یکسان، `id` ترتیب را قطعی می‌کند. شمارش و خواندن هر صفحه در یک دستور SQL با `count(*) OVER()` و در نتیجه در یک snapshot انجام می‌شوند. صفحه‌بندی از نوع offset است؛ تغییر هم‌زمان داده‌ها بین دو درخواست صفحه می‌تواند جای رکوردها را تغییر دهد.

```json
{
  "contacts": [],
  "pagination": { "page": 1, "pageSize": 20, "total": 0, "totalPages": 0 }
}
```

`page` از ۱ تا ۱۰۰۰۰ و `pageSize` از ۱ تا ۱۰۰ است؛ پیش‌فرض‌ها ۱ و ۲۰ هستند. پارامترهای ناشناخته یا تکراری رد می‌شوند. ایندکس‌های موجود مالک/نام و مالک/شماره حفظ شده‌اند. جست‌وجوی substring و تشخیص تکراری‌ها پس از محدودسازی به مالک، محاسبه می‌شوند؛ برای دفترچه‌های بسیار بزرگ، ایندکس expression یا `pg_trgm` باید بر اساس اندازه‌گیری اضافه شود.

## تشخیص تکراری و ادغام

تشخیص بر اساس نام یکسانِ نرمال‌شده یا شماره یکسانِ نرمال‌شده است؛ تطبیق فازی نیست.

- **نرمال‌سازی شماره:** جداکننده‌ها حذف و ارقام فارسی یکسان می‌شوند.
- **شماره‌های ایرانی:** از فاز ۹ به شکل ملی مقایسه می‌شوند. `+98 912…`، `0098 912…`، `0912…` و `912…` یک شماره‌اند. شماره ثابت با پیش‌شماره (`+98 21…` و `021…`) هم همین‌طور است.
- **شماره‌های دیگر:** رقم‌به‌رقم مقایسه می‌شوند.
- **مقدار ذخیره‌شده:** این نرمال‌سازی فقط در تشخیص است و شماره ذخیره‌شده عوض نمی‌شود. جست‌وجو هم مثل قبل روی ارقام تایپ‌شده انجام می‌شود.

خروجی تشخیص شامل `groups` و `pagination` است. اعضای هر گروه به ترتیب زمان ساخت می‌آیند (قدیمی‌ترین اول).

گروهی که با `POST /api/contacts/duplicates/ignore` و بدنه `{ "contactIds": [...] }` نادیده گرفته شود، در `by=phone` دیگر نمی‌آید تا وقتی عضو تازه‌ای به آن اضافه شود.

- **ورودی:** ۲ تا ۲۰ شناسه متمایز.
- **پاسخ موفق:** ۲۰۴.
- **شناسه ناموجود یا متعلق به کاربر دیگر:** ۴۰۴.
- **شناسه‌هایی که یک گروه شماره نیستند:** ۴۰۹ `NOT_DUPLICATES`. هر گروه `by`، `value`، `count`، `contacts` و `hasMore` دارد. حداکثر ۲۰ مخاطب نمونه از هر گروه برگردانده می‌شود؛ برای گروه بزرگ‌تر از جست‌وجو و صفحه‌بندی فهرست استفاده کنید. صفحه‌بندی گروه‌ها نیز همان محدودیت‌های فهرست را دارد.

```json
{
  "targetId": "UUID مقصد",
  "sourceIds": ["UUID مخاطب دیگر"],
  "overrides": { "name": "نام انتخاب‌شده", "reminder": "یادداشت نهایی" }
}
```

- در هر درخواست ۲ تا ۲۰ مخاطب متمایز قابل ادغام‌اند. ادغام دستی فقط بعد از انتخاب صریح شناسه‌ها انجام می‌شود.
- نام و شماره مقصد حفظ می‌شوند؛ می‌توان آن‌ها را در `overrides` تعیین کرد. مدل فعلی یک شماره دارد، بنابراین شماره متفاوت منابع پس از ادغام نگه‌داری نمی‌شود و فرانت باید پیش‌نمایش انتخاب شماره ارائه کند.
- تاریخ تولد و عکس خالی مقصد از اولین منبع دارای مقدار، با ترتیب ثابت شناسه، پر می‌شوند. تاریخ تولد را می‌توان صریحاً در `overrides` انتخاب یا پاک کرد.
- یادداشت‌های متفاوت با خط جدید ترکیب می‌شوند. اگر بیش از ۲۰۰۰ کاراکتر شوند، پاسخ ۴۰۹ می‌آید و چیزی تغییر نمی‌کند؛ کاربر باید یادداشت نهایی را در `overrides` انتخاب کند.
- مقصد باقی می‌ماند و منابع حذف می‌شوند؛ پاسخ `{ contact, mergedCount }` است. شمارش شامل مقصد است.
- همه شناسه‌ها باید متعلق به کاربر باشند. وجود حتی یک منبع ناموجود یا متعلق به دیگری، کل تراکنش را لغو می‌کند. قفل مالک در همه تغییرات مخاطب، از مصرف هم‌زمان یک منبع در دو ادغام جلوگیری می‌کند.

## عکس و Cloudinary

سرویس فعال پروژه Cloudinary است. [راهنمای ثبت‌نام رایگان و اتصال](cloudinary-setup.fa.md) را ببینید. ثبت‌نام رایگان کارت بانکی نمی‌خواهد؛ مصرف پلن رایگان محدود است. کلیدها فقط در `.env` بک‌اند قرار می‌گیرند:

```dotenv
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
```

پس از تغییر تنظیمات، `docker compose up -d backend` را اجرا کنید. هیچ کلیدی نباید به فرانت یا `NEXT_PUBLIC_*` برسد. unsigned upload preset لازم نیست؛ سرور درخواست آپلود را امضا می‌کند.

درخواست آپلود، `multipart/form-data` با یک فایل به نام `photo` و هدر `Origin` برابر `APP_ORIGIN` است. فرانت با `FormData` و `credentials: 'include'` درخواست می‌فرستد و Content-Type را دستی تعیین نمی‌کند. فقط JPEG، PNG و WebP ثابت تا ۵ MiB و ۲۰ میلیون پیکسل پذیرفته می‌شوند. تصویر decode می‌شود، metadata آن حذف و در ابعاد حداکثر ۱۰۲۴×۱۰۲۴ به WebP تبدیل می‌شود. SVG، تصویر متحرک و فایل جعلی رد می‌شوند. محدودیت آپلود ۲۰ درخواست در ۱۵ دقیقه برای هر IP و در حافظه هر نمونه است.

فایل با نوع `authenticated` و شناسه تصادفی `contacts/<userId>/cloudinary/<uuid>` ذخیره می‌شود. ستون عمومی‌نشدهٔ `photoKey` همین شناسه پایدار را نگه می‌دارد؛ ستون `photoUrl` برای عکس جدید null است. پاسخ API در فیلد `photoUrl` لینک امضاشدهٔ `private_download_url` با اعتبار ۵ دقیقه دارد. لینک فقط بعد از بررسی مالکیت تولید می‌شود و در فهرست، جزئیات، تکراری‌ها و پاسخ تغییرات یکسان است. فرانت برای تمدید لینک منقضی‌شده دوباره اطلاعات مخاطب را می‌گیرد. لینک تا پایان اعتبار برای هر کسی که آن را داشته باشد قابل استفاده است؛ خروج از حساب لینک قبلی را فوراً باطل نمی‌کند.

طبق مستندات Cloudinary، این لینک‌های موقت از API تحویل داده می‌شوند، روی CDN cache نمی‌شوند و مصرف پهنای‌باند آن‌ها دو برابر delivery عادی حساب می‌شود. این انتخاب برای حفظ محدودیت دسترسی است؛ قبل از گسترش مصرف، quota را بررسی کنید. [مستندات دسترسی موقت](https://cloudinary.com/documentation/control_access_to_media)

هنگام جایگزینی، حذف یا ادغام، عکس‌های کنارگذاشته‌شده پاک می‌شوند و عکس منتقل‌شده به مقصد حفظ می‌شود. شکست ذخیره در دیتابیس باعث تلاش برای حذف فایل تازه می‌شود. شکست پاک‌سازی، تغییر موفق دیتابیس را لغو نمی‌کند؛ پیام `PHOTO_CLEANUP_REQUIRED` با شناسه فایل در لاگ ثبت می‌شود. retry خودکار و صف پایدار در این فاز وجود ندارد.

بدون کلیدهای Cloudinary، آپلود پاسخ `503 PHOTO_STORAGE_NOT_CONFIGURED` دارد؛ CRUD مخاطبین بدون عکس کار می‌کند. تست‌های API از سرویس جایگزین استفاده می‌کنند و تست‌های SDK امضای واقعی لینک را با کلید ساختگی بررسی می‌کنند. تست آپلود واقعی به حساب و کلیدهای کاربر نیاز دارد.

بازگشت از S3 به Cloudinary به مایگریشن جدید نیاز ندارد: `photoKey` شناسه داخلی عمومی سرویس ذخیره‌سازی است. شناسه‌های قدیمی S3 به‌اشتباه در Cloudinary امضا یا حذف نمی‌شوند؛ در صورت وجود فایل واقعی S3، انتقال فایل‌ها باید جداگانه انجام شود. مایگریشن‌های قبلی برای حفظ تاریخچه دست‌نخورده‌اند.

## مایگریشن و تست

```bash
npm run db:migrate
npm run test:contacts
npm run check
```

مایگریشن اولیه عکس، collation الفبایی را اضافه کرده است. مایگریشن `20260929110000_s3_photos` نام ستون داخلی فایل را به `photoKey` تغییر می‌دهد. اگر شناسه Cloudinary قبلی وجود داشته باشد، مایگریشن با خطای صریح متوقف می‌شود تا فایل‌های قبلی بدون انتقال، S3 فرض نشوند. PostgreSQL باید ICU داشته باشد.

تست `test:contacts` با Jest و Supertest روی PostgreSQL واقعی اجرا می‌شود؛ `DATABASE_TEST_URL` باید دیتابیس توسعه/تست مایگریت‌شده باشد. تست‌ها دو کاربر موقت با کوکی JWT واقعی می‌سازند، همه داده‌های همان دو کاربر را در پایان حذف می‌کنند و به حساب‌های موجود دست نمی‌زنند. نبودن متغیر تست باعث شکست صریح می‌شود و هیچ تستی مخفیانه skip نمی‌شود. `npm run check` تست‌های بدون دیتابیس را اجرا می‌کند؛ جایگزین `test:contacts` نیست.

پوشش شامل CRUD، مرز دسترسی A/B، دورزدن مالکیت از طریق ورودی، جست‌وجوی فارسی/شماره، ترتیب و صفحه‌بندی، ورودی نامعتبر، ادغام اتمیک و هم‌زمان، upload/replace/delete عکس، فایل جعلی/بزرگ، CSRF، rate limit و شکست سرویس عکس است. Jest در حالت ESM با `--experimental-vm-modules` اجرا می‌شود.
