# فاز چهار: API مخاطبین

همه مسیرها زیر `/api/contacts` هستند و کوکی معتبر `contacts_session` می‌خواهند. اگر کاربر 2FA را فعال کرده باشد، نشست بدون تأیید مرحله دوم پذیرفته نمی‌شود. `userId` از نشست سرور گرفته می‌شود؛ فرانت اجازه ارسال یا تغییر آن را ندارد. شناسه مخاطب متعلق به کاربر دیگر، دقیقاً مانند شناسه ناموجود، پاسخ `404 CONTACT_NOT_FOUND` دارد.

## مسیرها

| متد    | مسیر                                  | کاربرد                     |
| ------ | ------------------------------------- | -------------------------- |
| GET    | `/api/contacts?q=&page=1&pageSize=20` | فهرست، جست‌وجو و صفحه‌بندی |
| POST   | `/api/contacts`                       | ساخت مخاطب                 |
| GET    | `/api/contacts/:id`                   | دریافت یک مخاطب            |
| PATCH  | `/api/contacts/:id`                   | تغییر فیلدهای ارسال‌شده    |
| DELETE | `/api/contacts/:id`                   | حذف مخاطب؛ پاسخ ۲۰۴        |
| POST   | `/api/contacts/:id/photo`             | آپلود یا جایگزینی عکس      |
| DELETE | `/api/contacts/:id/photo`             | حذف عکس مخاطب              |
| GET    | `/api/contacts/duplicates?by=phone`   | گروه‌های شماره تکراری      |
| GET    | `/api/contacts/duplicates?by=name`    | گروه‌های نام تکراری        |
| POST   | `/api/contacts/merge`                 | ادغام مخاطبین انتخاب‌شده   |

API ساخت/ویرایش و ادغام فقط JSON می‌پذیرد. پاسخ ساخت مخاطب ۲۰۱ است؛ خواندن، ویرایش، عکس و ادغام ۲۰۰ هستند. فیلدهای پاسخ مخاطب: `id`، `name`، `phone`، `photoUrl`، `birthday`، `reminder`، `createdAt` و `updatedAt`. کلید داخلی S3 و شناسه مالک در پاسخ عمومی نمایش داده نمی‌شوند.

## ساخت و ویرایش

```json
{
  "name": "سارا احمدی",
  "phone": "+۹۸ (۹۱۲) ۳۴۵-۶۷۸۹",
  "birthday": "2000-02-29",
  "reminder": "همکار قدیمی"
}
```

نام و شماره برای ساخت اجباری‌اند؛ تاریخ تولد و یادداشت اختیاری هستند. نام پس از trim حداکثر ۲۰۰ کاراکتر و بدون نویسه کنترلی است. شماره ۳ تا ۱۵ رقم دارد تا شماره‌های کوتاه هم پشتیبانی شوند؛ `+` فقط در ابتدا مجاز است. ارقام فارسی/عربی به لاتین تبدیل و فاصله، پرانتز، نقطه و خط تیره حذف می‌شوند. مثال بالا به `+989123456789` تبدیل می‌شود. این اعتبارسنجی ساختاری است و فعال‌بودن شماره را تضمین نمی‌کند.

تاریخ تولد ورودی `YYYY-MM-DD` و تاریخ واقعی میلادی است؛ پاسخ تاریخ، ISO در نیمه‌شب UTC است و فرانت باید آن را به‌صورت تاریخ بدون تبدیل منطقه زمانی نمایش دهد. یادداشت حداکثر ۲۰۰۰ کاراکتر است. با `null` می‌توان تاریخ تولد یا یادداشت را پاک کرد. PATCH خالی، فیلد ناشناخته، `userId`، `id`، `photoUrl` و `photoKey` رد می‌شوند؛ عکس فقط از مسیر آپلود مدیریت می‌شود.

## جست‌وجو و صفحه‌بندی

```text
/api/contacts?q=علي&page=1&pageSize=20
/api/contacts?q=۹۱۲-۳۴۵&page=1&pageSize=10
```

جست‌وجوی نام شامل بخشی از نام، بدون حساسیت به بزرگی حروف لاتین و با یکسان‌سازی `ي/ی` و `ك/ک` است. جست‌وجوی شماره ارقام فارسی/عربی و جداکننده‌ها را یکسان می‌کند. `%` و `_` نویسه عادی‌اند، نه wildcard؛ کوئری‌ها پارامتری هستند. جست‌وجو هیچ‌گاه مخاطبین دیگر کاربران را برنمی‌گرداند.

مرتب‌سازی الفبایی با collation مبتنی بر ICU در PostgreSQL انجام می‌شود و حروف فارسی مانند «ب، پ، ت، چ» درست مرتب می‌شوند. برای نام‌های یکسان، `id` ترتیب را قطعی می‌کند. شمارش و خواندن هر صفحه در یک snapshot انجام می‌شوند. صفحه‌بندی از نوع offset است؛ تغییر هم‌زمان داده‌ها بین دو درخواست صفحه می‌تواند جای رکوردها را تغییر دهد.

```json
{
  "contacts": [],
  "pagination": { "page": 1, "pageSize": 20, "total": 0, "totalPages": 0 }
}
```

`page` از ۱ تا ۱۰۰۰۰ و `pageSize` از ۱ تا ۱۰۰ است؛ پیش‌فرض‌ها ۱ و ۲۰ هستند. پارامترهای ناشناخته یا تکراری رد می‌شوند. ایندکس‌های موجود مالک/نام و مالک/شماره حفظ شده‌اند. جست‌وجوی substring و تشخیص تکراری‌ها پس از محدودسازی به مالک، محاسبه می‌شوند؛ برای دفترچه‌های بسیار بزرگ، ایندکس expression یا `pg_trgm` باید بر اساس اندازه‌گیری اضافه شود.

## تشخیص تکراری و ادغام

تشخیص بر اساس نام یکسانِ نرمال‌شده یا شماره یکسانِ بدون جداکننده است؛ تطبیق فازی نیست. پیش‌شماره کشور حدس زده نمی‌شود: `0912...` و `+98912...` خودکار یک گروه نیستند. خروجی تشخیص شامل `groups` و `pagination` است. هر گروه `by`، `value`، `count`، `contacts` و `hasMore` دارد. حداکثر ۲۰ مخاطب نمونه از هر گروه برگردانده می‌شود؛ برای گروه بزرگ‌تر از جست‌وجو و صفحه‌بندی فهرست استفاده کنید. صفحه‌بندی گروه‌ها نیز همان محدودیت‌های فهرست را دارد.

```json
{
  "targetId": "UUID مقصد",
  "sourceIds": ["UUID مخاطب دیگر"],
  "overrides": { "name": "نام انتخاب‌شده", "reminder": "یادداشت نهایی" }
}
```

- در هر درخواست ۲ تا ۲۰ مخاطب متمایز قابل ادغام‌اند. ادغام دستی فقط بعد از انتخاب صریح شناسه‌ها انجام می‌شود.
- نام و شماره مقصد حفظ می‌شوند؛ می‌توان آن‌ها را در `overrides` تعیین کرد. مدل فعلی یک شماره دارد، بنابراین شماره متفاوت منابع پس از ادغام نگه‌داری نمی‌شود و فرانت باید پیش‌نمایش انتخاب شماره ارائه کند.
- تاریخ تولد و عکس خالی مقصد از اولین منبع دارای مقدار، با ترتیب ثابت شناسه، پر می‌شوند. تاریخ تولد را می‌توان صریحاً در `overrides` انتخاب یا پاک کرد.
- یادداشت‌های متفاوت با خط جدید ترکیب می‌شوند. اگر بیش از ۲۰۰۰ کاراکتر شوند، پاسخ ۴۰۹ می‌آید و چیزی تغییر نمی‌کند؛ کاربر باید یادداشت نهایی را در `overrides` انتخاب کند.
- مقصد باقی می‌ماند و منابع حذف می‌شوند؛ پاسخ `{ contact, mergedCount }` است. شمارش شامل مقصد است.
- همه شناسه‌ها باید متعلق به کاربر باشند. وجود حتی یک منبع ناموجود یا متعلق به دیگری، کل تراکنش را لغو می‌کند. قفل مالک در همه تغییرات مخاطب، از مصرف هم‌زمان یک منبع در دو ادغام جلوگیری می‌کند.

## عکس و Amazon S3

[راهنمای قدم‌به‌قدم ساخت حساب، bucket و دسترسی](s3-setup.fa.md) را ببینید. بک‌اند از SDK رسمی AWS و bucket خصوصی S3 استفاده می‌کند. تنظیمات فقط در `.env` ریشه هستند:

```dotenv
AWS_REGION=eu-central-1
S3_BUCKET=نام-bucket-خودتان
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
AWS_SESSION_TOKEN=
```

در استقرار روی AWS می‌توان به‌جای کلید ثابت از IAM Role و credential provider chain استاندارد SDK استفاده کرد. `AWS_SESSION_TOKEN` فقط برای credential موقت است. هیچ کلیدی نباید به فرانت یا `NEXT_PUBLIC_*` برسد. پس از تغییر تنظیمات، `docker compose up -d backend` را اجرا کنید.

درخواست آپلود، `multipart/form-data` با یک فایل به نام `photo` و هدر `Origin` برابر `APP_ORIGIN` است. هدر Origin برای multipart اجباری است تا CSRF کنترل شود. فرانت با `FormData` و `credentials: 'include'` درخواست می‌فرستد و `Content-Type` را دستی تعیین نمی‌کند.

فقط JPEG، PNG و WebP ثابت، حداکثر ۵ MiB و ۲۰ میلیون پیکسل پذیرفته می‌شوند. تصویر واقعاً decode شده، جهت آن اصلاح، metadata حذف و در ابعاد حداکثر ۱۰۲۴×۱۰۲۴ به WebP تبدیل می‌شود. SVG، تصویر متحرک و فایل جعلی رد می‌شوند. محدودیت آپلود ۲۰ درخواست در ۱۵ دقیقه برای هر IP و در حافظه هر نمونه سرور است.

فایل با کلید تصادفی `contacts/<userId>/<uuid>.webp` و رمزنگاری SSE-S3 ذخیره می‌شود؛ هیچ ACL عمومی ارسال نمی‌شود. **Block all public access باید روی bucket روشن بماند** و Object Ownership روی Bucket owner enforced باشد. ستون `photoKey` کلید پایدار فایل را نگه می‌دارد؛ لینک امضاشده در دیتابیس ذخیره نمی‌شود و ستون `photoUrl` برای عکس‌های جدید null است.

در پاسخ API، فیلد `photoUrl` پس از بررسی مالکیت با لینک GET امضاشده و اعتبار ۵ دقیقه پر می‌شود. این رفتار در فهرست، جزئیات، تکراری‌ها و پاسخ تغییرات یکسان است. فرانت برای تمدید لینک منقضی‌شده دوباره اطلاعات مخاطب را می‌گیرد. `photoKey` فیلد مستقلی در پاسخ عمومی ندارد، هرچند مسیر فایل طبیعتاً در URL دیده می‌شود. لینک امضاشده تا پایان اعتبار برای هر کسی که خود لینک را داشته باشد قابل استفاده است؛ خروج از حساب لینک قبلی را فوراً باطل نمی‌کند. Cache-Control تصویر private و حداکثر ۶۰ ثانیه است.

هنگام جایگزینی، حذف یا ادغام، فایل‌های کنارگذاشته‌شده از S3 حذف می‌شوند؛ عکس منتقل‌شده به مقصد حفظ می‌شود. اگر ذخیره در دیتابیس پس از آپلود شکست بخورد، فایل تازه پاک می‌شود. اگر پاک‌سازی S3 شکست بخورد، تغییر موفق دیتابیس برگردانده نمی‌شود؛ پیام `PHOTO_CLEANUP_REQUIRED` و کلید فایل برای پیگیری در لاگ ثبت می‌شود. retry خودکار و صف پایدار در این فاز وجود ندارند؛ قطع پردازش یا قطع پاسخ upload نیز ممکن است فایل بدون مرجع باقی بگذارد.

بدون region یا bucket، آپلود پاسخ `503 PHOTO_STORAGE_NOT_CONFIGURED` دارد. شکست آپلود پاسخ ۵۰۲ و ناتوانی در تولید لینک پاسخ ۵۰۳ دارد. CRUD مخاطبین بدون عکس به حساب S3 نیاز ندارد. تست‌های API از سرویس جایگزین استفاده می‌کنند؛ تست‌های SDK امضای واقعی URL را با credential ساختگی و بدون درخواست AWS بررسی می‌کنند. تأیید آپلود واقعی فقط بعد از آماده‌شدن حساب و bucket امکان‌پذیر است.

## مایگریشن و تست

```bash
npm run db:migrate
npm run test:contacts
npm run check
```

مایگریشن اولیه عکس، collation الفبایی را اضافه کرده است. مایگریشن `20260929110000_s3_photos` نام ستون داخلی فایل را به `photoKey` تغییر می‌دهد. اگر شناسه Cloudinary قبلی وجود داشته باشد، مایگریشن با خطای صریح متوقف می‌شود تا فایل‌های قبلی بدون انتقال، S3 فرض نشوند. PostgreSQL باید ICU داشته باشد.

تست `test:contacts` با Jest و Supertest روی PostgreSQL واقعی اجرا می‌شود؛ `DATABASE_TEST_URL` باید دیتابیس توسعه/تست مایگریت‌شده باشد. تست‌ها دو کاربر موقت با کوکی JWT واقعی می‌سازند، همه داده‌های همان دو کاربر را در پایان حذف می‌کنند و به حساب‌های موجود دست نمی‌زنند. نبودن متغیر تست باعث شکست صریح می‌شود و هیچ تستی مخفیانه skip نمی‌شود. `npm run check` تست‌های بدون دیتابیس را اجرا می‌کند؛ جایگزین `test:contacts` نیست.

پوشش شامل CRUD، مرز دسترسی A/B، دورزدن مالکیت از طریق ورودی، جست‌وجوی فارسی/شماره، ترتیب و صفحه‌بندی، ورودی نامعتبر، ادغام اتمیک و هم‌زمان، upload/replace/delete عکس، فایل جعلی/بزرگ، CSRF، rate limit و شکست سرویس عکس است. Jest در حالت ESM با `--experimental-vm-modules` اجرا می‌شود.
